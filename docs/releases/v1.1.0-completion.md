documentation. New source modules cover structured errors, retry policy,
circuit breakers, provider-cache quarantine, database recovery, persistent

## 2. Architecture changes

The implementation retains the Version 1 package boundaries. Shared schemas
define errors, retries, health, maintenance, updates, and the additive MCP
contract. Providers own HTTP classification, isolated circuit state, validated
fallback, and cache quarantine. SQLite owns schema 6 resilience state,
diagnostics, backup/restore, and scheduler leases. The MCP composition root
wires these services into local, desktop, and hosted surfaces.

## 3. Error-code registry

The central registry contains 62 unique `GC-<DOMAIN>-<NUMBER>` codes across
configuration, network, provider, validation, cache, database,
synchronisation, scheduler, update, MCP, AI, hosted, security, and unknown
domains. Runtime validation, bounded cause chains, UUID trace IDs, stable
serialization, and secret/path/header/stack redaction apply at every public
boundary. The complete registry is in
[error-codes.md](../errors/error-codes.md).

## 4. Self-healing mechanisms

Automatic recovery is limited to bounded retry, healthy-provider fallback,
labelled last-known-good cache fallback, transactional rollback, interrupted
job recovery, verified database restoration, and read-only safe mode. Every
attempt has a trace ID, timestamps, observable outcome, cooldown, and terminal
limit. No recovery path changes RuneScape gameplay or silently deletes player
data.

## 5. Retry policies

The shared policy implements exponential backoff, bounded jitter,
`Retry-After`, cancellation, maximum attempts, and maximum elapsed time.
Timeouts, connection failures, 429s, and eligible 5xx responses retry.
Configuration, authentication, schema, and validation failures do not.

## 6. Circuit-breaker policies

Circuits are isolated by provider and capability. The default threshold is
three failures, the initial cooldown is 30 seconds, and cooldown growth is
capped at five minutes. States are `closed`, `open`, and `half-open`; only a
bounded probe is admitted after cooldown. Diagnostics exposes all state and one
confirmed circuit can be reset without affecting other providers.

## 7. Provider fallback behaviour

The existing deterministic provider priority order remains intact. A failed
preferred provider is classified and retried only when safe. An open circuit is
skipped, the next configured provider is validated independently, and returned
metadata identifies fallback provenance. Contradictory values are never merged.

## 8. Cache fallback behaviour

Fresh validated records return normally. During eligible temporary failures,
last-known-good records may return with a stale flag, original storage time,
age/freshness windows, refresh error code, and next retry. Live-only,
cross-player, unsupported-schema, failed-integrity, and quarantined records
cannot use stale fallback. Malformed records are stored only as bounded,
redacted quarantine metadata.

## 9. Database recovery behaviour

Database opening checks integrity and migration state. File-backed upgrades
create and verify a local backup before schema changes. Each migration and
`user_version` update is transactional. Failed or interrupted upgrades restore
only from a verified backup; ambiguous or destructive situations preserve the
original database and enter safe mode for explicit review.

## 10. Safe-mode behaviour

Safe mode preserves read-only access, diagnostics, and safe profile export
where possible while disabling background writes, migrations, and optional AI
startup. It never resets the database. Leaving safe mode requires the health
condition to be resolved and an explicit action.

## 11. Scheduler behaviour

SQLite persists job definitions, last/next timestamps, leases, attempts,
history, failures, and recovery state. Startup catches up missed or stale jobs
without blocking valid cached operation. Atomic leases prevent duplicate
processes, concurrency is bounded, shutdown cancels cleanly, interrupted jobs
recover, offline mode pauses network work, and five failed recovery attempts
move a job to the permanent `failed` state until a manual retry.

## 12. Automatic refresh intervals

Defaults are configurable:

| Data                      |    Default |
| ------------------------- | ---------: |
| Player Hiscores           | 15 minutes |
| Current GE prices         |  5 minutes |
| GE item catalogue         |    6 hours |
| GE history                |     1 hour |
| RuneScape news            |     1 hour |
| Quest revisions           |   24 hours |
| Training-method revisions |   24 hours |
| Static XP tables          |     7 days |
| Software updates          |   24 hours |

The persistent maintenance jobs currently schedule quest and training refreshes
every 24 hours, price-catalogue refresh every 6 hours, and update checks every
24 hours. More granular provider caches retain their shorter freshness policy.

## 13. Update-checker behaviour

The checker reads the documented GitHub Releases list API, ignores drafts and
pre-releases by default, validates semantic versions and official HTTPS asset
URLs, exposes notes/dates/assets/checksums, and caches validated metadata for
24 hours. Offline and disabled modes perform no request. Temporary failure may
show labelled cached metadata. It never downloads, installs, stages, or
executes an update.

integrity, lock, and restore cases are covered.

The declared range is `^22.0.0 || ^24.0.0` across all first-party packages.
Runtime checks, CI, release workflows, Docker, `.nvmrc`, and documentation use

tests, and 95 hardening tests.

## 21. Security considerations

Public errors and diagnostics redact credentials, tokens, cookies, private
headers, absolute paths, raw database/provider contents, prompts, and stacks.
Retries and requests are bounded. Hosted operator tools preserve authorization
and tenant isolation. Update metadata is read-only and constrained to official
GitHub URLs. The lockfile forces the patched `brace-expansion` 5.0.8 transitive
dependency, and `pnpm audit --audit-level high` reports no known
vulnerabilities. Rust formatting, clippy with warnings denied, and all Rust
tests pass. No gameplay automation or client instrumentation was introduced.

## 22. Privacy considerations

Maintenance reads only public RuneScape data selected by the user. Diagnostics
do not export profiles or private identifiers. Quarantine retains a content
hash and bounded redacted sample rather than full payloads. Live monitoring
does not publish the test display name, endpoints, headers, or responses.

## 23. Backward-compatibility results

The 48 Version 1.0 MCP tool names, order, effects, and strict input schemas
remain the prefix of Version 1.1. The original Version 1.0 manifest is frozen.
Profile export remains version 1, provider plugin API remains version 1, and
database upgrades retain existing data. Protocol tests continue to use Version
1.0 clients against the Version 1.1 server.

## 24. Known limitations

- Live provider availability remains outside application control.
- GitHub update results cannot advertise a release before maintainers publish
  one.
- Platform signing and Apple notarization require maintainer credentials.
- Version 1.1 remote cross-platform results require a pushed branch or tag.
- Optional Ollama and LM Studio daemon smoke tests require those local services.
- `better-sqlite3` 12.x still uses the audited, install-time-only
  `prebuild-install` 7.1.3 fallback. Its known deprecation is explicitly allowed
  until the new database major completes compatibility validation.
- Database restore that could discard user-created information remains a
  backup-first, explicit manual operation.
