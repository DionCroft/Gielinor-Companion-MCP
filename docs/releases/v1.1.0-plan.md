## Scope and invariants

Version 1.1 extends the existing production architecture. It does not rebuild or
replace Version 1.0.

The following boundaries remain stable:

- all 48 Version 1.0 MCP tool names and existing input/output fields;
- profile export schema Version 1;
- provider plugin API Version 1;
- existing player profiles, quest progress, catalogues, and valid cache rows;
- local-first and offline operation;
- the desktop, hosted service, Ollama, LM Studio, and optional Alt1 surfaces;
- read-only RuneScape gameplay behavior.

No recovery path may invent RuneScape data, silently replace valid data with
malformed or incomplete data, delete player data, conceal stale/fallback data,
or interact with the RuneScape client.

The branch includes the tested desktop startup and live player-progress fix from
PR #16. Before the V1.1 branch is published, it will be rebased or retargeted
onto `main` after that prerequisite is merged.

## Audit findings

Version 1.0 already provides useful foundations:

- bounded HTTP attempt counts, exponential delay, `Retry-After`, and request
  coalescing;
- deterministic priority-based provider fallback and result validation;
- fresh/stale cache windows with stale-while-revalidate;
- per-provider success/failure counters and latency;
- transactional catalogue replacement and suspicious-truncation guards;
- transactional forward-only SQLite migrations, WAL, busy timeout, and manual
  backup support;
- visible catalogue sync status and offline preferences;
- safe hosted health endpoints and redacted operational logs.

The V1.1 gaps are:

- error codes are package-specific strings without one validated public model;
- retries lack jitter, cancellation propagation, total elapsed-time bounds, and
  shared failure classification;
- provider health is not a circuit breaker and is not persisted;
- stale fallback does not carry a structured refresh error or next retry;
- malformed cache/provider data is deleted or rejected rather than quarantined;
- database integrity, verified restore, interrupted migration recovery, and
  safe mode are not centrally coordinated;
- no persistent scheduler, startup stale check, or automatic first-run
  catalogue population exists;
- diagnostics are split across catalogue cards and hosted readiness;
- the desktop update page is static;
- live provider tests are manual only;
- Node.js 20 remains declared even though it reached end of life on
  2026-03-24.

## Architectural decisions

### Shared structured errors

The stable schema, code registry, redaction rules, trace IDs, serialization, and
unknown-error normalization will live in `@gielinor/shared-types`. This avoids
dependency cycles and makes the same validated envelope available to core,
providers, database, MCP, hosted, desktop, agent runtime, update checks,
scheduler, and overlay.

Existing package error classes will become compatibility wrappers around the
shared model. Public MCP/HTTP/UI errors will contain no stack, secret, token,
private header, raw database content, private player data, or personal absolute
path. Secure local logs may retain a stack separately.

### Core resilience services

Pure orchestration will live in `@gielinor/core`:

- retry policy and failure classifier;
- provider-independent circuit breaker;
- recovery policy and bounded repair coordinator;
- trace context and recovery history;
- scheduler policy and health aggregation;
- maintenance and update-check use cases expressed through narrow ports.

Provider implementations will supply network-specific classification and
validated data. Database implementations will supply persistence and locking.

### Database schema Version 6

One additive migration is planned for:

- persistent scheduler jobs and leases;
- recovery/error events;
- provider circuit state;
- quarantine metadata and bounded redacted samples;
- maintenance preferences and safe-mode state;
- cached software release metadata.

The migration will create a verified backup before file-database upgrade,
remain transactional, preserve all Version 1.0 tables and JSON, and include
fresh, upgrade, rollback, locked, interrupted, backup, integrity, and restore
tests. Automatic restore will only use a verified backup and will never discard
user-created data. Any ambiguous recovery enters safe mode and requires explicit
confirmation.

### MCP contract Version 1.1

`MCP_TOOL_NAMES_V1` and `data/contracts/mcp-tools-v1.json` remain frozen at 48
tools. A new additive Version 1.1 list and manifest will append:

1. `get_system_health`
2. `get_provider_health`
3. `get_catalogue_health`
4. `list_recent_errors`
5. `list_recovery_events`
6. `retry_failed_operation`
7. `refresh_stale_catalogues`
8. `run_database_integrity_check`
9. `export_redacted_diagnostics`
10. `check_for_software_updates`

Potentially destructive repairs will not be exposed over MCP. Compatibility
tests will prove that the original 48 names, order, schemas, effects, and
profile export remain unchanged.

### Node.js support

Version 1.1 will raise the supported minimum to Node.js 22 and test Node.js 22
and 24. Node.js 20 is officially end-of-life, while 22 and 24 are supported LTS
lines as of this plan. The root/workspace engines, runtime validation, docs,
Docker image, CI matrix, release workflow, and desktop sidecar policy will be
made consistent. Node.js 26 will not be claimed until it reaches LTS and is
tested.

Official lifecycle source:
<https://nodejs.org/en/about/previous-releases>

## Default maintenance policy

All values will be configurable and validated.

| Data or operation              | Default freshness |
| ------------------------------ | ----------------: |
| Player Hiscores                |        15 minutes |
| Current GE prices              |         5 minutes |
| GE item catalogue              |           6 hours |
| GE historical data             |            1 hour |
| RuneScape news                 |            1 hour |
| Quest revision check           |          24 hours |
| Training-method revision check |          24 hours |
| Static XP tables               |            7 days |
| Software update check          |          24 hours |

Defaults also include bounded concurrency, per-provider budgets, automatic
startup refresh, configurable background refresh, offline/live-only modes,
maximum recovery attempts, cooldowns, and clean shutdown. Missed jobs are
evaluated at the next startup; jobs never require continuous execution.

## Vertical delivery slices

Each slice must build and pass its focused deterministic tests before the next
slice begins.

### 1. Structured errors

- Add the validated error registry and public envelope.
- Add redaction, trace IDs, bounded causes, serializers, and compatibility
  wrappers.
- Map core, provider, database, MCP, hosted, agent, and overlay errors.
- Create error-code and troubleshooting documentation.

### 2. Retry and provider resilience

- Add shared failure classification.
- Add exponential backoff, jitter, elapsed limit, cancellation, and
  `Retry-After`.
- Add isolated closed/open/half-open circuit breakers and persisted health.
- Preserve deterministic provider fallback and make fallback provenance
  explicit.

### 3. Cache fallback and quarantine

- Add schema/integrity validation to cached records.
- Attach stale timestamps, refresh errors, and next retry to safe fallback.
- Enforce live-only and player-isolation rules.
- Quarantine malformed payload metadata without exposing secrets or activating
  invalid data.

### 4. Database recovery and safe mode

- Add integrity, migration-state, WAL, lock, backup, and restore diagnostics.
- Back up before the Version 6 migration.
- Add interrupted-migration recovery and verified restore.
- Enter persistent safe mode rather than resetting or deleting ambiguous data.

### 5. Persistent scheduler

- Persist last/next run, lease, status, attempts, cooldown, and history.
- Add duplicate-process locking, bounded concurrency, catch-up, interruption
  recovery, clean shutdown, offline/rate-limit/circuit awareness, and manual
  retry.
- Use one logical shared-catalogue lease in hosted mode.

### 6. Automatic population and refresh

- Implement the seven visible first-run stages.
- Populate missing quest, training, and GE catalogues independently.
- Preserve partial success and keep valid sections usable.
- Run non-blocking startup stale checks and configurable background refresh.

### 7. Health and diagnostics

- Aggregate database, provider, catalogue, scheduler, update, and optional AI
  states into the six documented overall states.
- Add a desktop diagnostics centre and safe recovery controls.
- Add redacted export with bounded logs and sanitized configuration.

### 8. MCP Version 1.1

- Add twelve strict diagnostics/maintenance tools, including confirmation-gated
  expired-quarantine cleanup and a single-circuit reset.
- Return trace IDs, timestamps, recovery status, and structured failures.
- Exercise every tool through the real MCP protocol boundary.

### 9. Read-only update checker

- Add a GitHub Releases provider using the documented API.
- Validate metadata and semantic versions; ignore prereleases by default.
- Cache success for 24 hours, honor offline/disabled modes, expose checksums
  where published, and never download or install code.

### 10. Monitoring and compatibility

- Add scheduled/manual live contract monitoring for Hiscores, ItemDB, Wiki
  quests/training, GE current/history, and GitHub Releases.
- Classify transient outages separately from schema/application failures.
- Upload only redacted diagnostics and keep normal pull-request CI deterministic.
- Add the Node 22/24 compatibility matrix.

### 11. Fault injection and release preparation

- Add deterministic timeout, DNS, 429, 500, empty, malformed, slow, lock,
  migration, interruption, cache corruption, scheduler crash, and update outage
  cases.
- Update all required architecture, testing, installation, security, privacy,
  roadmap, changelog, MCP, and release documents.
- Version every workspace and native/container surface as `1.1.0`.

## Per-slice checks

At minimum, affected slices run:

```sh
corepack pnpm format:check
corepack pnpm lint
corepack pnpm typecheck
corepack pnpm test
corepack pnpm build
```

Focused scripts will be added for errors, resilience, recovery, scheduler,
update checking, fault injection, and live monitoring. Existing provider,
database, MCP, desktop, hosted, AI, hardening, release, E2E, overlay, load,
Rust, contract, docs, clean-install, container, and native gates remain active.

## Completion rule

Version 1.1.0 will not be marked complete, tagged, or described as released
while any mandatory gate fails, any error code is undocumented, any recovery
loop is unbounded, invalid data can replace valid data, repair can silently
delete player data, the original 48-tool contract changes, offline startup
fails, or stale/fallback use is hidden.
